باشه. این «UX Spec رسمی» را طوری می‌نویسم که اگر یک CTO بداخلاق بخواند، نتواند بگوید «این UI راه دورزدن است». این سند، UI/UX محصولیِ براق نیست؛ این یک UX حاکمیتیِ غیرقابل‌تفسیر است که همه قفل‌ها را enforce می‌کند. 🔒

عنوان: UX Specification — Governance Console و Interaction Layer (Non-Executable / Advisory UI)
شناسه: ARZIN-AGENTOS-UX-SPEC-v1.0
دامنه: فاز ۱ و فاز ۲ (قفل)
اصل طلایی: «هیچ ورودی انسانی (Voice/Text) و هیچ خروجی AI مستقیماً AACP publish عملیاتی نمی‌کند.»

۱) هدف و جایگاه این UI
این UI صرفاً برای «حاکمیت، پیشنهاد، بازبینی انسانی، و ثبت Audit» ساخته می‌شود. هدف آن اجرای سریع کارها نیست. هدف آن حذف هرگونه اجرای بی‌صاحب و ساختن زنجیره پاسخ‌گویی است. این UI باید به گونه‌ای طراحی شود که حتی اگر کاربر عجله داشته باشد یا سیستم خطا کند، مسیر امن و قابل حسابرسی حفظ شود.

۲) تعریف Non-Executable UI
Non-Executable یعنی در این UI هیچ دکمه، مسیر یا API وجود ندارد که بتواند «اجرای عملیاتی» را مستقیم فعال کند. UI فقط می‌تواند سه چیز انجام دهد: دریافت ورودی (Voice/Text)، نمایش پیشنهاد/ترجمه نیت، و ثبت تصمیم انسانی به عنوان «درخواست Permit». Execute فقط بعد از صدور Permit معتبر و از مسیر AACP انجام می‌شود و UI حق دور زدن این زنجیره را ندارد.

۳) نقش‌ها و مجوزها
این UI باید Role-based باشد و نقش‌ها از هم جدا باشند. نقش پیشنهادی حداقلی شامل Operator (عملیات)، Governance Admin (حاکمیت)، Auditor (حسابرسی)، Security (امنیت) و Executive Viewer (مدیریت ارشد) است. Operator حق تغییر Policy ندارد. Auditor حق تأیید اجرایی ندارد. Governance Admin حق اجرای مستقیم ندارد. Executive Viewer فقط مشاهده و گزارش می‌گیرد. هر نقش باید Scope مشخص در Policy Plane داشته باشد و UI فقط همان Scope را نمایش دهد.

۴) جریان ورودی Text
کاربر متن را وارد می‌کند. سیستم Intent پیشنهادی تولید می‌کند. Intent در قالب ساختاریافته نمایش داده می‌شود. کاربر می‌تواند Intent را اصلاح کند. سپس «تأیید نهایی انسان» گرفته می‌شود. نتیجه این تأیید نهایی به صورت «Permit Request» ثبت می‌شود. UI در هیچ مرحله‌ای پیام عملیاتی publish نمی‌کند. UI فقط یک درخواست Permit می‌سازد و به Permit Service می‌دهد. اگر Permit صادر شد، Execution Layer از مسیر AACP اقدام می‌کند و نتیجه در Audit Sink ثبت می‌شود و سپس UI فقط نتیجه را نمایش می‌دهد.

۵) جریان ورودی Voice
Voice فقط پس از شناسایی مدیر با MFA مجاز است. سپس سیستم Voice را دریافت می‌کند و «ترجمه نیت» تولید می‌کند. ترجمه نیت باید به مدیر نمایش داده شود. مدیر باید قادر باشد آن را اصلاح کند. سپس تأیید نهایی مدیر گرفته می‌شود. بعد از تأیید نهایی، یک Permit Request ساخته می‌شود. Voice هرگز مستقیم publish نمی‌کند و حتی در صورت تشخیص مثبت/منفی غلط، تا زمانی که مدیر روی Intent تأیید نهایی نزند، هیچ اتفاقی نمی‌افتد. اگر ترجمه نیت یا تشخیص هویت مشکوک باشد، سیستم باید Fail-Closed کند و فقط امکان بازگشت به متن یا تکرار ورودی را بدهد.

۶) ساختار صفحه‌های اصلی
صفحه‌ها باید کم و دقیق باشند. صفحه اول «Inbox پیشنهادها» است؛ یعنی پیشنهادهای ایجنت‌ها و رویدادهای نیازمند توجه انسانی. صفحه دوم «Intent Review» است؛ یعنی نمایش Intent ساختاریافته، Policy Scope، پیامدها، و مسیر Audit. صفحه سوم «Permit Decision» است؛ یعنی تأیید/رد/تعلیق با ثبت دلیل. صفحه چهارم «Trace & Evidence» است؛ یعنی مسیر پیام، chain_hash، امضا، نسخه Policy، و شواهد. صفحه پنجم «Policy View» فقط مشاهده است مگر برای نقش حاکمیتی مجاز. صفحه ششم «Operational Console» برای وضعیت کانال‌ها، DLQ، و نرخ Reject است و هیچ دکمه اجرایی ندارد، فقط کنترل‌های ایمن مثل Rate-limit توصیه‌ای و مشاهده.

۷) قواعد نمایش پیشنهادها
هر پیشنهاد باید با این اجزا نمایش داده شود: خلاصه پیشنهاد، Confidence، Impact estimate، Evidence references، Policy scope مرتبط، محدودیت‌ها، و وضعیت مجاز بودن. UI باید اولویت‌بندی را نشان دهد، ولی اجازه ندهد کاربر «اجرای فوری» انجام دهد. هر پیشنهاد باید دقیقاً به یک Agent ID و Agent version و schema_version متصل باشد و اگر هرکدام Missing باشد، پیشنهاد اصلاً نمایش داده نشود یا به عنوان Invalid با دلیل مشخص نمایش داده شود.

۸) قواعد سخت برای دکمه‌ها و اکشن‌ها
در کل UI فقط این اکشن‌ها مجاز هستند: Create/Update Intent Draft، Approve/Reject Intent، Create Permit Request، View Trace، Export Audit Report. هر اکشن باید Audit envelope خودش را تولید کند. هیچ اکشنی که معادل «publish به topic اجرایی» باشد وجود ندارد. حتی Approve هم فقط «Permit Request» تولید می‌کند و نه «Execute».

۹) اتصال به AACP و جداسازی Control/Data Plane
UI فقط با سرویس‌های Control Plane حرف می‌زند: Registry/Identity، Policy Plane، Permit Service، Audit Query، Recommendation Plane، Intent Gateway. UI نباید به Data Plane یا Kafka access مستقیم داشته باشد. اگر لازم باشد وضعیت Kafka دیده شود، از طریق Observability Service ارائه می‌شود، نه دسترسی مستقیم به Broker.

۱۰) مدیریت خطا و Fail-Closed
در هر خطا، UI باید Fail-Closed کند. اگر امضا Verify نشود، اگر chain_hash موجود نباشد، اگر policy_scope mismatch باشد، اگر permit_status غیرمجاز باشد، اگر schema_version ناشناخته باشد، نتیجه باید «رد و ثبت» شود. UI باید دلیل رد را انسانی و قابل دفاع نمایش دهد و Trace را لینک کند. هیچ حالت «Ignore and continue» نباید وجود داشته باشد.

۱۱) الزامات Audit در سطح UI
هر تعامل کاربر باید یک Event در Audit ایجاد کند، شامل actor_id، role، session_id، action، timestamp_ms، intent_hash، policy_version، و trace_id. برای Voice باید audio_fingerprint یا reference ذخیره شود، نه الزاماً خود صوت خام، مگر سیاست ذخیره‌سازی اجازه دهد. خروجی باید قابل ارائه به Auditor و رگولاتور باشد. UI باید بتواند برای هر تصمیم انسانی، «Chain of Custody» را نمایش دهد.

۱۲) الزامات امنیتی UI
MFA برای نقش‌های حساس اجباری است. Session باید کوتاه و قابل ابطال باشد. RBAC/ABAC باید enforce شود. همه ارتباطات mTLS داخل Private Cloud انجام می‌شود. UI نباید کلید خصوصی امضا یا توکن‌های حساس را نگه دارد. Signing و verification در سرویس‌های امن انجام می‌شود. UI فقط وضعیت verification را نمایش می‌دهد.

۱۳) الزامات کارایی و تجربه
هدف UI سرعت زیبایی نیست، سرعتِ پاسخ‌گویی قابل دفاع است. برای Inbox و Review، p95 زیر ۱.۵ ثانیه برای بار معمولی قابل قبول است. در صورت کندی، UI باید degrade کند ولی مسیر حاکمیتی را نشکند. برای Executive View، روایت مدیریتی باید خلاصه، قابل چاپ، و قابل ارجاع باشد.

۱۴) تعریف Done و معیار پذیرش
این UI زمانی Done است که هیچ مسیری برای publish عملیاتی بدون Permit انسانی وجود نداشته باشد، و هر اقدام کاربر یک Audit record کامل بسازد، و هر پیشنهاد بدون امضا/زنجیره/Policy معتبر اصلاً قابل تأیید نباشد. همچنین باید بتوانیم حداقل سه سناریوی Fail را در Test Harness نشان دهیم: Intent tamper، policy drift، و signature invalid که هر سه باید Reject شوند و DLQ/Trace داشته باشند.

۱۵) مرزبندی با UI/UX اصلی محصول
UI/UX اصلی محصول شامل داشبوردهای براق، روایت‌های چندلایه، تجربه Marketplace، و ابزارهای بهره‌وری است. آن‌ها فقط وقتی مجازند که Control Plane قفل و پایدار باشد و Gate فاز ۲/۳ باز شود. تا آن زمان، هر UI که «راحت‌تر اجرا کند» یعنی عقب‌گرد حکمرانی.

اگر بخواهی همین را تبدیل می‌کنم به یک «سند رسمی قابل ارائه» با شناسه، نسخه، امضا و پیوست‌های کنترلی، و بعدش هم یک «Backlog UI» دقیق برای تیم Frontend/Backend/DevOps که بدون ابهام پیاده‌سازی کنند.
